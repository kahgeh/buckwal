# Glossary

One line per term, as the code on this branch uses it: the meaning, then "Not:", the words not to use for it. Specs, code, logs, settings and docs use these terms and no others for the same thing. The README has the full rules. Words that older text still uses are listed at the end, under "Not yet consistent".

- **buckwal**: the product: the library `buckwal`, the CLI `buckwal` and the server `buckwal serve`.
- **durable**: a commit is durable when a log record holding it is in the bucket (and in the local fsynced file). `execute` and `COMMIT` return `Ok` only then. Not: saved, persisted, flushed, synced (a local fsync alone is not durable).
- **ack (acked)**: the `Ok` a commit returns once it is durable; a commit that returned an error is not acked. Not: committed (for a commit still waiting), confirmed (that word is for ops and records in the bucket).
- **head**: the bucket object `head`, flat JSON: `format`, `generation`, `manifest`, `writer_id`, `epoch` (and `journal_mode` in formats 2 and 3, `lease_ms`, `request_timeout_ms` and `next_generation_floor` when set, `key_check` and `integrity` in format 3). It says where the database is now (`format/head.rs`). Not: manifest (a different object), pointer, root, state file (that is the local state).
- **generation**: one stretch of the log between two seals. Log records live in `log/<generation>/<seq>`, and a restore reads only the head's generation. Not: epoch (a different counter), version, segment, era.
- **seal**: the end-of-generation upload: a seal-start record, then every page that changed in the generation (`pages/…`), then a manifest, then the head moved to the next generation with `If-Match`. WAL mode seals when the WAL restarts, MVCC mode in `LogDurableStorage::truncate`. Not: checkpoint (a local engine step that may trigger a seal), flush, snapshot, rollover.
- **seal-start record**: an empty log record (zero syncs) a seal appends first, so a writer that was taken over collides with the fence before it uploads a page. Not: seal marker, barrier.
- **pending seal**: a seal whose head write had an unknown result, so the head may or may not name the next generation. It makes the bucket degraded until it is adopted. Not: half-sealed, failed seal (a seal that is known not to have published is a failed seal and the generation simply continues).
- **adopt**: accept a pending seal whose head turned out to be published, and move on to the next generation without uploading again (the next commit's sync does it, so does the checkpoint start). Not: recover, repair, resume, catch up (`catch_up` is the code's name for settling what is owed, which includes more than an adopt).
- **manifest**: `manifest/<generation>`, written at a seal: the page size and count and the generation that holds each page's latest copy. Not: head, index, catalog.
- **log record**: one object `log/<generation>/<seq>`: magic, kind, writer id, syncs of ops, then a `sha256` trailer (an integrity code in an encrypted bucket). Kind 1 holds `app.db-wal` extents, kind 2 is a fence record, kind 3 (format 2 only) holds `app.db-log` extents. Not: log object (except as a count: `log_objects`), segment, entry, chunk.
- **kind 3 record**: a log record of kind 3, which holds `app.db-log` extents. It exists only in a format 2 bucket; a format 1 bucket refuses it. Not: MVCC record, WAL record (that is kind 1), commit record.
- **in doubt**: a log record whose PUT result is unknown, so it may or may not be in the bucket; the next sync settles it before anything else. Not: pending (that word is for a seal), lost, uncertain.
- **epoch**: a counter in the head. A new database starts at 1, a takeover writes the next one, every other writer open raises it by one, so a late head PUT from an earlier process fails its `If-Match`. Not: generation, term, version, salt (the WAL header's salt bytes).
- **fence**: a record (kind 2) a takeover appends to the log. Any writer whose append collides with it, or whose head check finds another writer, gets `Fenced` and stays fenced. Not: lock (the lock is `durable.lock`, a local file), kill, revoke, evict.
- **lease**: how long (default 30 s, `BUCKWAL_LEASE_MS`) a writer trusts its last confirmation that the head is its own. Past it, the next append reads the head first. Not: TTL, lock, heartbeat.
- **takeover quiet** (also: quiet): the wait after a fence before the new writer seals a generation whose old writer may still be uploading a seal: the larger of the old writer's and the new writer's `lease` + `request_timeout`, from the head's `lease_ms` and `request_timeout_ms`, capped at `MAX_SEAL_QUIET` (`seal_quiet_ms`, `TakeoverReport::quiet`). Not: takeover wait, quiet period, grace (that is `trim_grace`, a different wait), cooldown.
- **takeover**: restoring a database and writing the head with a new writer id at the next epoch, then a fence record. The old writer is fenced for good. Not: failover, promotion, switchover, steal.
- **claim**: a writer open of a restored or empty directory takes the database over with a new writer id (the claim id, persisted before the head write so a crash resumes it). Not: acquire, adopt (that word is for a pending seal), register.
- **writer id**: 16 random bytes in hex that name one writer in the head and in every record. A new database and every takeover get a new one. Not: node id, process id, owner, client id.
- **restore**: rebuilding a database directory from the bucket alone: the head, the manifest and the generation's log. It writes nothing to the bucket, and pages come lazily on first read. Not: recover (recovery is the engine's own crash recovery), replicate, clone, download.
- **restored copy**: a database directory made by `restore`. Not: standby, mirror (a *replica* is a different thing: it keeps following the bucket).
- **image**: what the bucket holds of one local file for a generation (the `app.db-wal` image from kind 1 records, the `app.db-log` image from kind 3 records). Not: snapshot, copy, backup.
- **reconcile**: on a writer open, comparing each local file with the bucket's image of the generation: **Level** (equal), **Behind** (the local file is shorter, so the bucket's image replaces it), **Ahead** (the local file is longer, so the difference is uploaded) or **NewGeneration** (the bucket sealed since, so the image replaces the file). Done per file (`app.db-wal`, and `app.db-log` in MVCC). Not: sync, repair (the repair of a log shorter than its header is a separate step), merge.
- **GC and trim**: deletion of log records, manifests and pages the head no longer reaches, once the bucket's own clock says they have been unreferenced longer than the trim grace. `gc` runs one pass from anywhere, a writer runs it on its own thread. Not: cleanup, compaction, vacuum, retention.
- **batching (Off, Window)**: `Off` uploads every commit on its own. `Window` shares one upload between commits waiting up to `max_wait`, `max_commits` or `max_bytes`. Window is refused in MVCC mode. Not: group commit (the engine's own batching in MVCC mode), buffering, coalescing.
- **group commit**: the MVCC engine's own batching: concurrent commits are written by one lead with one sync, so one kind 3 record carries the group. Not: Window, batch, bulk commit.
- **journal mode**: whether a database is a WAL database (`JournalMode::Wal`, the default) or an MVCC one (`JournalMode::Mvcc`). It is chosen when the database is created, written to the head (format 2) and never changed. Not: storage mode, engine mode, `PRAGMA journal_mode` as a way to switch (switching is refused).
- **WAL mode**: a database in journal mode Wal, durable at the sync of `app.db-wal`. Not: default mode, classic mode, single-writer mode.
- **MVCC**: turso's concurrent-writes journal mode. A database created new in MVCC mode is durable here (bucket format v2). An existing WAL database is never switched to it. Not: concurrent mode, multi-writer mode.
- **`BEGIN CONCURRENT`**: the MVCC transaction that lets several writers run at once. Write conflicts fail with `Write-write conflict` and are retried. Use it for every write in MVCC mode. Not: optimistic transaction, `BEGIN IMMEDIATE`.
- **hybrid design**: the MVCC design of `docs/mvcc-recon.md` (hybrid C): the commit point at the `.db-log` sync through a file wrapper, the seal in a `DurableStorage` wrapper, the WAL carrying only checkpoint frames. Not: option C, mixed mode.
- **`LogShippingFile`**: the wrapper around `app.db-log`. It records writes as ops and at `sync` uploads the unconfirmed ones as a kind 3 record before the local fsync (`io/log_file.rs`). Not: log file (that is `app.db-log`), WAL file, `ShippingFile` (that wraps `app.db-wal`).
- **`DurableStorage` wrapper**: `LogDurableStorage`, given to the engine with `OpenOptions::durable_storage`. It delegates to the engine's `Storage`, except that `truncate` seals first and a checkpoint failure after a seal poisons the database (`io/log_storage.rs`). Not: storage hook, log wrapper (that is `LogShippingFile`).
- **commit point**: the step after which a commit is durable: the `app.db-wal` sync in WAL mode, the `app.db-log` sync in MVCC mode. In both the bucket upload comes before the local fsync. Not: WAL (for the MVCC commit point), checkpoint, commit time.
- **confirmed-sync rule**: a `.db-log` sync returns `Ok` only when every op recorded so far is confirmed in the bucket. Unsent ops are kept for the next sync and in-doubt ones are settled first. Not: write-through rule, ack rule.
- **op**: one recorded write or truncate of a local file, shipped inside a log record. Not: operation, mutation, delta.
- **whole-log ship**: the first sync after an open or a generation change sends the whole local `app.db-log` from offset 0, because the generation's image must equal the file (`ship_whole_file_next`). Not: full backup, resync, initial upload.
- **high-water mark**: the highest offset plus length written to a local file since it was last cut (the file's size at open); maintenance reads it as the `-wal` size in WAL mode and the `app.db-log` size in MVCC mode (`Engine::wal_bytes`). Not: file size, WAL size (for the `.db-log` in MVCC mode), offset.
- **poison**: after a checkpoint failed once its seal had succeeded, the database refuses writes, checkpoints and seals until it is reopened, because the engine may hold the new salt while the file keeps the old frames (`LogDurableStorage::on_checkpoint_end`). Not: fence (that is about another writer), corrupt, lock, read-only.
- **speculative read**: in MVCC mode a read inside `BEGIN` or `BEGIN CONCURRENT` can see another connection's commit while its upload is in flight. Autocommit reads wait out the upload. Not: dirty read, early read.
- **outcome unknown**: what an error from a commit means: it may or may not be in the bucket. In MVCC mode the commit also stays in the local database and the next commit ships it. Not: rolled back (true only in WAL mode with Off), failed, lost.
- **format v1 / v2 / v3**: the bucket format. v1 is every plaintext WAL bucket (record kinds 1 and 2). v2 is plaintext MVCC only: the head has `"format":2` and `"journal_mode":"mvcc"`, and kind 3 records exist. v3 is every encrypted bucket, WAL or MVCC: the head has `"format":3`, `key_check` and an integrity code, and pages, log records and manifests carry integrity codes. An older build refuses a head of a format it does not know. Not: version 1/2 (a bare "version" is the engine's or the crate's), schema.
- **maintenance checkpoint**: a background `TRUNCATE` checkpoint that seals a generation the engine never restarts, triggered by log objects or by bytes (the `-wal` in WAL mode, the `app.db-log` in MVCC mode). Not: auto-checkpoint (the engine's own, which this library turns off in MVCC), compaction.
- **dirty file**: `app.db-dirty`, the page numbers checkpointed since the last seal, fsynced before `app.db` is, so a seal after a crash still uploads them. Not: dirty set (the in-memory set), changelog.
- **local state**: `app.db-durable`, JSON in the database directory: writer id, generation, completeness, claim, epoch and the takeover quiet (`"format":2` for an MVCC directory). Not: head (that is the bucket's), metadata file, lock file.
- **staging directory**: `app.db-creating`, inside the database directory, where a new MVCC database is built before the bucket sees anything; it is never opened again and the next open removes it (`create.rs`). Not: temp directory, scratch, tmp.
- **follow the head**: the CLI uses the journal mode the bucket's head names when given neither `--journal-mode` nor `BUCKWAL_JOURNAL_MODE` (one head GET); the library never does. Not: auto-detect, sniff.
- **SQL over HTTP v3**: tursodb's protocol that `buckwal serve` speaks (`serverless/PROTOCOL.md`). Not: Hrana, libSQL protocol, REST (see Not yet consistent for the test client's name).
- **replica**: a local copy of the database on another machine that follows the bucket and only reads (`open_replica`, `buckwal follow`). Not: follower database, read copy, mirror, standby (a restored copy is a one-time copy, not a replica).
- **replica mode**: how the library opens a directory for a replica: local writes from the follower only, no upload, no seal, no claim, no GC (the third IO mode, ADR 0006). Not: read-only mode (that is `verify`'s open).
- **follower**: the replica's thread that runs sync passes and applies frames. Not: syncer, tailer, applier.
- **sync pass**: one run of the follower: list the log, fetch, apply the committed prefix, check the head. A notification or the slow poll starts it. Not: poll (a sync pass can be started by a notification).
- **slow poll**: the replica's timer (`BUCKWAL_REPLICA_POLL_MS`, 60 s by default) that starts a sync pass when no notification came. Not: reconcile (in this repo `reconcile` levels a local directory with the bucket's image on a writer open, see its entry), heartbeat.
- **position file**: `app.db-replica`: the replica's generation, stage, frame offset and replica id. Not: cursor, checkpoint file, watermark.
- **committed prefix**: the frames of a rebuilt WAL image up to its last commit frame; only these are applied. Not: applied tail.
- **NotificationSource**: the follower's internal interface that says "wake up", fed by the webhook listener (or an app's own call). In the code it is the `ReplicaWaker` handle (`Replica::waker()`, `wake()`). Not: notifier, event bus.
- **integrity key**: the key derived from the encryption key with HKDF-SHA256 (RFC 5869) and a fixed label, used only for integrity codes and `key_check`; never the page cipher's key, never stored or logged (`encryption.rs`). Not: MAC key, HMAC key, signing key.
- **integrity code**: the 32-byte HMAC-SHA256 on an encrypted bucket's page object, log record, manifest or head. A failed one is `Corrupt("integrity: <object key>")` and the `integrity check failed` record. Not: tag (in this repo a tag is a log record op type, README "tag 1, a write"), MAC, signature, checksum (that is the plaintext SHA-256 trailer).
- **key_check**: the format 3 head's 16 bytes of HMAC-SHA256 under the integrity key over a fixed label. It says which key a bucket was written with, and is compared at open before any integrity code, so a wrong key is an `Encryption` error and never counts as tampering. Not: key hash, key id, fingerprint.
- **skipped generation**: the generation number after a takeover that never gets a log: the new writer's first seal writes its pages and manifest under it and moves the head one past it, so they never share keys with the fenced old writer's seal. Not: gap generation, missing generation.
- **next generation floor**: the head's `next_generation_floor`: the generation a seal moves the head to after a takeover, at the least (a seal moves it to `max(G + 1, floor)` and writes under one below that). It stays in every later head, and GC trusts no manifest below `floor - 1` (the oldest manifest GC may trust). Not: minimum generation, generation base.

## Not yet consistent

Older text keeps words this glossary says not to use. ADRs and records keep their words as written, so they are listed here instead of reworded; for the rest, the next change that touches the text rewords it.

- **WAL for the MVCC commit path.** README, How it works, Commits, Generations and Restore describe the commit and the seal in WAL terms ("the WAL's fsync", "when the engine restarts its WAL", "rebuilds the WAL from the log") and only point to MVCC mode. README, Bucket format v1 (`log/…` row) says "one WAL fsync when Off". D3 and D6 in README, Decisions, say "the WAL's fsync" and "the write that restarts the WAL". They are true for WAL mode.
- **`wal_bytes` holding the `.db-log` mark.** The field `Config.maintenance_wal_bytes`, the variable `BUCKWAL_MAINTENANCE_WAL_MIB`, the event field `MaintenanceStarted.wal_bytes`, the log field `wal_bytes=` and the span attribute `buckwal.wal_bytes` hold the high-water mark of the `app.db-log` in MVCC mode (`maintenance.rs`, README, Maintenance checkpoint and Telemetry). The names are public settings and telemetry and stay as they are.
- **"epoch" for the WAL header's salt bytes.** `crates/buckwal/src/io/wal_file.rs` (the `EPOCH` range, "a new epoch", "a header with a new epoch") and `docs/mvcc-recon.md` ("a WAL header epoch change") use "epoch" for bytes 12 to 24 of the `-wal` header. The glossary's epoch is the head's counter.
- **"Checkpoint" for the seal.** README, Costs (Stage 2: batching), "Checkpoint uploads", and README, Limits 4 ("The checkpoint's upload") call the seal's upload a checkpoint's. The checkpoint is the engine step that triggers it in WAL mode and contains it in MVCC mode.
- **"adopt" for taking over a file.** README, Use (the directory cases) says an existing SQLite or tursodb file "cannot be adopted"; the glossary's adopt is for a pending seal.
- **"replica".** `docs/read-replicas-recon.md` (and its mention in README, Layout) is the investigation that came before the replica work. It uses "replica" and "follower" loosely, and keeps its words. "Promote" is not a term: making a replica's machine the writer is a takeover.
- **"Hrana".** The crate and directory `crates/buckwal-hrana-client` and README, Server (Protocol, "the protocol descends from libSQL's Hrana") use the protocol's old name. The crate name is historical (CLAUDE.md says so) and stays.
- **`docs/mvcc-recon.md` wording.** It uses "the head is the commit point" for the seal (Stage-2 design, Creation) next to "commit point" for the `.db-log` sync, and "seal at the WAL truncate" for the old WAL-mode path. It is a design record and keeps its words.
