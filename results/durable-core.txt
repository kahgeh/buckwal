Boundary cost: a seal runs inside the write that restarts the WAL, so the commit that crosses
a generation boundary waits for that generation's whole page upload. With the default
automatic checkpoint this commit came about every 500 commits here (about 2 WAL frames per commit).
- Slowest commit: #502, 69.8 ms (p50 1.33 ms). It is most likely the commit that crossed the
  first boundary (inferred: bench does not record which commit triggered a seal); that seal
  (seal_1) took 39.4 ms for 169 pages. bench does not break down the rest.
- Each in-run seal against its page count: 169 p 39.4 ms, 170 p 38.2, 170 p 37.2, 172 p 37.4,
  172 p 44.3, 171 p 38.6, 171 p 37.2, 172 p 39.1, 172 p 38.0, 171 p 37.0 (16 PUTs in parallel,
  then the manifest PUT and the head PUT). Each of those 10 commits took at least its seal's
  time; all of them sit above p99 (2.05 ms).
- The close seal (8 pages) took 4.4 ms.
- Log PUTs: one per acked commit, plus one per WAL restart (the WAL header's own sync):
  5010 = 5000 + 10.

Restore (5000-commit prefix, generation 12, 1673 pages):
- 33 ms, 4 GETs (head, manifest, page 1 for the MVCC check, 1 log object = 3 + log_objects),
  1 LIST, 4651 bytes downloaded. No page is fetched at restore time.
- Pages arrive lazily on first read: verify (PRAGMA integrity_check, which reads every page)
  of a fresh restore took 0.52 s wall, process start included, and left all 1673 pages local.
- The restored copy holds all 5000 rows (count 5000, ids 0..4999).
