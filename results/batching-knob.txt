# One run per configuration; no repeats, so treat small differences as noise.
#
# Workload (bench): CREATE TABLE bench(id INTEGER PRIMARY KEY, payload BLOB) on one connection,
# which is then closed; then 2000 autocommit INSERT OR REPLACE statements of a 1024-byte blob,
# ids 0..1999, shared by --connections threads (one connection each, ids handed out from
# one counter); each thread closes its connection when the ids run out; then the database is
# closed. Default settings otherwise (upload concurrency 16, prefetch off, trim grace 10 min).
# --batching is set with Database::set_batching after open; no connection sets its own.
#
# Keys:
# - commit_p50/p95/p99_ms: latency of each bench INSERT as the caller saw it (lock waits,
#   local write, upload and ack wait included).
# - commits_acked, commits_uploaded, log_puts, log_put_bytes, commits_per_log_put,
#   bytes_per_log_put: Database::upload_stats() after the commit threads finished (so after
#   the last connection's close-time TRUNCATE) minus the snapshot taken after the CREATE TABLE.
#   upload_stats counts the WAL-header record of each WAL restart as a commit: one after the
#   setup close's TRUNCATE, one per in-run restart, one at the last connection's close. That
#   is why commits_acked is 2002-2005 for 2000 bench commits.
# - ack_wait_p50/p95/p99_ms: the upload_stats histogram since open (the CREATE TABLE's one
#   ack is included; a histogram cannot be subtracted). Each is the upper edge of its
#   histogram sub-bucket (at most 6.25 % above the true value).
# - log_puts_per_commit = log_puts / 2000 (log PUTs per acked bench commit).
# - bucket_puts: every PUT the store saw, setup included. page_puts: PUTs to pages/.
# - seal_N_ms / seal_N_pages: each checkpoint upload. seal_1 (2 pages) is the setup
#   connection's close, before the measured commits; the last seal is the close-time
#   TRUNCATE of the last bench connection; the ones between are in-run WAL restarts after
#   the engine's automatic checkpoint (every 1000 WAL frames).
#
# Commands (DURABLE_* from scripts/rustfs.sh env; DURABLE_OTEL and DURABLE_BATCHING unset;
# run id 1792179518; <tmp> from mktemp -d, removed afterwards):
#   for C in 1 8; for B in off 'window 1ms 64 1MiB' 'window 10ms 64 1MiB' 'window 50ms 64 1MiB':
#     DURABLE_PREFIX=bench/stage2/c<C>-<off|window-Nms>-1792179518 \

What the figures show:
- Off: one log PUT per acked commit (1.002 = one per commit plus one per WAL restart), with 1
  or 8 connections. 8 Off connections reach about the same throughput as one (631 vs 721
  commits/s): each commit holds the WAL write lock until its PUT returns.
- A single connection gains nothing from a window: it has at most one commit waiting, so
  every PUT still carries one commit (commits_per_log_put 1.002) and each commit waits the
  window on top of its PUT. Throughput falls from 721 to 363, 60 and 16 commits/s.
- With 8 connections a window shares PUTs: 3.1, 6.0 and 7.9 commits per log PUT at 1, 10 and
  50 ms (log PUTs per acked commit 0.32, 0.17, 0.13). Each connection has at most one commit
  waiting, so a PUT holds at most 8 here; max_commits 64 and max_bytes 1 MiB were (inferred) never the
  limit that fired. Only the 1 ms window raised throughput over Off (1038 vs 631 commits/s);
  10 and 50 ms traded throughput for fewer PUTs.
- Acks waited longer than max_wait plus one PUT (about 1.2 ms here) at the larger windows:
  ack wait p50 17.4 ms at 10 ms and 63.5 ms at 50 ms with one connection. The cause was not
  investigated. A review found no cause in the code; the excess grows with the window (about
  0.4, 5.6 and 11.8 ms at 1, 10 and 50 ms), which fits macOS timer coalescing on the
  uploader's recv_timeout (hypothesis, unverified).
- Commit latency with 8 Window connections is above the ack wait (p99 49-75 ms vs 4.9-73.7
  ms): it also includes waiting for the WAL write lock behind other connections.
- c8-off's slowest commit took 3086 ms (#8, near the start; p99 3.45 ms). It is most likely
  lock contention between the 8 connections at start-up (inferred; bench does not break it
  down).
- Checkpoint uploads (seals): with Off and one connection the automatic checkpoint restarted
  the WAL every ~500 commits and each seal took 41-45 ms for 170 pages, as in stage 1.
  Under Window with 8 connections no WAL restart happened in the run, so the whole run's
  pages (696-728) were sealed once, at the last connection's close, in 177-186 ms. With one
  Window connection the in-run seals took 43-75 ms for 170 pages.

Restore (the c1-off prefix: generation 6):
- 24 ms (0.04 s wall with process start), 4 GETs (head, manifest, page 1 for the MVCC check,
  1 log object = 3 + log_objects), 1 LIST, 4426 bytes downloaded. No page is fetched at
  restore time.
- verify (PRAGMA integrity_check, which reads every page lazily) of that fresh restore took
  0.23 s wall, process start included.
